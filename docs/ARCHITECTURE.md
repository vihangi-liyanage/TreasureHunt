# TreasureHunt Architecture

## System shape

The browser contains two presentation layers: React owns navigation, forms, menus, dialogs, and accessible HUD overlays; Phaser owns the canvas, physics, animation, and moment-to-moment play. They exchange small typed-by-convention JavaScript event payloads through a game bridge. Neither layer talks directly to PostgreSQL or the upstream Fish service.

Next.js Route Handlers form the server boundary. They validate the Supabase cookie session, authorise changes, call focused services, and return stable application responses. Supabase stores profiles, runs, checkpoints, challenge attempts, achievements, and completed scores under Row Level Security.

## Boundaries

| Area | Responsibility | Must not know |
| --- | --- | --- |
| `game/` | Deterministic rules, entities, systems, scenes, world configuration, domain events | React components, cookies, SQL, Fish response fields |
| `components/` and `app/` | Screens, forms, HUD, navigation, accessibility | Phaser internals, database implementation |
| `lib/supabase/` | Browser/server Supabase clients and session boundary | Game physics or Fish payloads |
| `lib/fish/` | Timeout, upstream fetch, response validation, normalisation | UI layout, checkpoint policy, score mutation |
| Route Handlers | Authentication, validation, orchestration, safe DTOs | Phaser sprites and scene lifecycle |

## Event-driven flow

Phaser input, overlaps, collisions, timers, and scene lifecycle callbacks create domain events such as `coin:collected`, `player:damaged`, `power:started`, `power:expired`, `world:completed`, and `run:ended`. Focused systems update local state once and the bridge publishes a serialisable snapshot to React. Scene shutdown must remove listeners and timers. A run state machine prevents duplicate completion or Game Over transitions.

Phase 3A implements this boundary in `game/core/game-bridge.js` and `game/core/events.js`. React sends only input, pause, resume, and restart commands. Phaser returns ready, state snapshot, completion, and game-over events. `GameScreen` never receives a scene, sprite, or physics object. `WorldScene` owns Arcade Physics and delegates input to `PlayerController`, patrol behaviour to `EnemySystem`, and deterministic score/lives/timer transitions to `RunState`. Scene shutdown destroys those systems and their bridge subscriptions before Phaser is destroyed.

The three files under `game/config/` are level data consumed by the reusable `WorldScene`; they contain art metadata, dimensions, platforms, coins, enemies, hazards, spawn, and typed goal positions rather than scene-specific control flow. `game/config/levels.js` is the small lookup contract. New worlds therefore add no copied scene, controller, combat service, HUD or persistence path.

## Phase 3B gameplay composition

`WorldScene` remains an event/lifecycle coordinator rather than a rule container. `PlayerController` owns keyboard/virtual input translation, acceleration, coyote time, buffering and animation selection. `InputState` tracks sources per control, so two touch pointers can hold movement and jump independently. `CombatState` owns the exact eight-second window, shot cooldown, pause shifting, repeated pickup and single expiry transition. `ProjectileSystem`, `EnemySystem`, and `CameraController` own their Phaser objects/listeners. The pure `collision-rules` module keeps stomp decisions testable without Phaser. Jump-envelope assertions remain test helpers because the former production `physics-model` had no runtime consumer and added a needless public module.

The render boundary is `load-assets.js` plus `create-textures.js`: the former knows project asset URLs and atlas geometry; the latter owns animation registration and measured presentation metadata. `getTerrainVisualLayout` converts the painted surface coordinate in each atlas frame to the configured Arcade collision top; hunter and enemy body offsets likewise use measured opaque baselines. World configuration never imports asset files, React or persistence. Generated terrain art remains separate from invisible collision strips, so correcting transparent padding or render origins does not change platform physics.

`WorldScene` owns Arcade collider registration, while `canLandOnPlatform` is a pure process predicate: contact resolves only for a descending body whose previous bottom was above the surface. `PlayerController` treats current downward contact or Arcade's resolved downward block as grounded. Gravity is configured once on the Arcade world and enabled through `player.body.setAllowGravity`, including after fall recovery; the body API matters because Phaser's display `Sprite` does not provide that method. Falling below the configured world margin remains an event-driven damage/recovery or Game Over transition.

Progression and a temporary run have different owners. `guest-progress.js` holds one guest adventure's ordered completed-world IDs in module memory and publishes small change events; it never writes progress to storage. Welcome resets that state and removes only the obsolete `treasurehunt.guest-progress.v1` key. Client-side Map ↔ Game navigation retains the active adventure, while refresh naturally creates a new one. A per-adventure attempt number changes the gameplay URL so `GameScreen`, Phaser, `RunState`, enemies and collectibles are reconstructed for every replay. Authenticated pages ignore this module and continue loading progress from Supabase.

The event ordering for a fish is overlap callback -> `CombatState.activate` -> `fish:collected` and `power:started` -> serialisable `state:changed` snapshot. F/touch input crosses as `input:changed`; `PlayerController` exposes a shoot action; `ProjectileSystem` emits `projectile:fired`; Arcade overlap disables the projectile/enemy before `enemy:defeated` and the updated snapshot. Expiry is edge-triggered once by `CombatState.consumeExpiry`. Completion first transitions `RunState`, pauses physics, publishes final state, then emits `world:completed`; React persists progression once. Terminal `RunState` guards reject duplicate mutations.

Scene shutdown owns bridge unsubscribe callbacks, Escape removal, resize removal and collider destruction. Phaser owns physics-group disposal; custom cleanup deliberately does not clear groups after Arcade Physics shutdown. The scene active clock clamps large throttled-frame deltas and stops while paused, preventing browser catch-up bursts from consuming the timer or power window.

## Phase 4 reuse and progression

`WorldScene` loads generic `world-panorama`, `world-terrain` and `world-objects` keys from the selected level's `art` metadata. Render modules still own atlas loading and animation; configuration supplies filenames, frame geometry and measured presentation values. `getTerrainVisualLayout` maps each painted surface to the configuration-owned Arcade collision top. `EnemySystem` accepts one presentation record because the scarab atlas has different transparent padding; it does not know which world selected it.

The route page resolves all three implemented worlds. For authenticated users it compares the requested world number with server-loaded `completed_worlds` before rendering. For guests, `GameScreen` checks the in-memory derived state before Phaser boot, so refresh or direct entry cannot restore or bypass the active-adventure sequence. Completion still emits once from Phaser; React sends `{ world, coins }` to `/api/progress`, which derives the player from verified cookie claims. No player ID crosses from gameplay.

Event ordering is unchanged across both worlds: overlap or collision updates deterministic state, emits a narrow domain event and snapshot, then React performs optional persistence. Restart uses the same level object and constructs new run state, enemies and collectibles. Scene shutdown owns command, keyboard, collider, system and resize cleanup. A separate `SunsetRuinsScene` or inheritance hierarchy would duplicate lifecycle behavior and let fixes diverge; the explicit configuration contract is smaller and easier to explain.

### Phase 4 terrain and fall correction

The Arcade bodies were not losing gravity. The Sunset terrain atlas had been reframed with large transparent borders, but its old full-frame surface rows and full-frame widths were still used. Consequently the static collision top rendered 19–35 world pixels above the painted stone, and invisible horizontal padding extended support beyond the visible edge. Several 60–90 pixel ground gaps were also short enough for the moving body to reach the next one-way strip before dropping beyond its 12-pixel landing tolerance.

`create-textures.js` now owns measured crop rectangles and converts crop-relative surface rows and opaque-width ratios into render geometry. Phaser registers trimmed frames from the existing licensed project atlas; level configuration still owns the actual collision rectangles. Both level configurations use deliberate 180–200 pixel ground gaps—inside the measured jump envelope but far enough that an unsupported body drops below the next platform tolerance—and keep enemy patrol endpoints over real ground. No hidden support collider was added. The same `WorldScene` and pure `canLandOnPlatform` rule therefore apply consistently to both worlds.

Falling remains an event, not a second physics system: the Arcade body leaves `blocked.down`, gravity advances it, `isBelowFallBoundary` detects one boundary crossing, and `RunState.damage` applies its existing invulnerability/terminal guard. A surviving player is returned with `body.reset`, which synchronises position, previous position, velocity and contact flags atomically before gravity is re-enabled. An alternative tilemap collision layer would provide authored contours and debug tooling, but converting the existing painted levels would be a disproportionate rewrite; per-platform rectangles plus measured presentation metadata are explicit and testable across all three worlds.

### Selected-world preload and readiness

The World Map previously used a button plus `router.push`, so Next had no visible `<Link>` to prefetch. After the dynamic game route mounted, `GameScreen` separately imported the Phaser chunk and only then let the scene request 6–7 MB of selected-world PNGs. The immediate full-screen loading overlay made even a cached boot flash “Preparing…”. In development, first navigation can additionally wait for on-demand Next route compilation; production uses build-time chunks and browser caching, so these measurements must not be conflated.

`game/preload-gameplay.js` is a focused browser boundary that knows only how to obtain the playable level's four asset URLs and dynamically import the game factory. `WorldMap` manually prefetches the selected unlocked route and starts that selected-world preload; it does not fetch locked worlds or move gameplay into Splash. The same cached promise is consumed by `GameScreen`, so repeated map/game transitions reuse the Phaser module and decoded browser resources. Failed promises are evicted for a genuine retry rather than cached as false success.

Readiness remains event-driven: prefetch is only an optimisation, Phaser's scene emits `game:ready` only after its real loader and `create` lifecycle finish, and the HUD timer does not start beforehand. The loading fallback is visually debounced for 250 ms, not delayed; it appears only when a real boot remains pending. Module/image failure or Phaser `loaderror` produces a recoverable error panel. Component cleanup still destroys its one game instance, bridge listeners and global input listeners. Keeping one global Phaser instance alive could make return navigation faster, but it would retain GPU/physics/input state across routes and complicate run reset; a service worker or global state manager is unnecessary for browser HTTP cache reuse.

Production-browser checks on the local build measured selected, fully warmed World 1/2 launches at approximately 0.77–0.81 seconds from Play to `game:ready`; the gameplay route showed one canvas and no loading overlay throughout its mounted loading state. Returning to the map removed the canvas, and replay produced a fresh 3-life/full-timer run. Development's first route visit can still be slower because Next compiles that route on demand; this is development tooling cost rather than a production asset/readiness regression.

## Phase 5 final-world composition

`crystal-cavern.js` is a third instance of the existing level-data contract: art/frame measurements, motion values, collision rectangles, collectibles, patrols, hazards and `{ type: "treasure", x, y }` goal. Worlds 1–2 use the same `goal` property with type `checkpoint`. `WorldScene.createGoal` is the only new branch: it selects presentation text/size from goal type, while the Arcade overlap, `RunState.complete`, physics pause, snapshot and `world:completed` bridge event remain shared. A separate final scene would duplicate collision, input, combat, timer and cleanup; a generic entity-component framework would add vocabulary without another runtime implementation.

Treasure ordering is overlap -> `RunState.complete()` -> physics pause and celebration -> final snapshot containing `completion: "treasure"` -> `world:completed` -> React overlay/persistence. `RunState` rejects a second completion because status is no longer `playing`; this prevents duplicate progression writes even if an overlap callback is queued twice. Reaching World 3, touching terrain or crossing an unrelated coordinate cannot complete it because no checkpoint body exists there.

The browser remains non-authoritative for numeric score. Authenticated treasure completion calls `/api/progress` with world and bounded coins only; the Route Handler derives identity from SSR claims and the service-role-only SQL function enforces sequential World 3 completion under RLS. No leaderboard run is automatically submitted. A server-replay/event-proof system could strengthen score authority but would add substantial protocol/storage complexity and is explicitly future work.

## Phase 8 achievements and verified rankings

Each authenticated world launch now requests one owned `game_runs` row through the verified SSR identity boundary. Phaser remains unaware of persistence: collision callbacks update `RunState` and emit narrow `coin`, `gem`, `fish`, `enemy`, and `objective` events. `GameScreen` serialises those events to the run Route Handler; the server validates the world and entity ID against the same immutable level configuration before a service-role-only SQL function records it once. Guest events instead update the existing in-memory adventure snapshot, which is reset on a new guest entry and never crosses into Supabase.

Completion ordering is objective overlap → terminal `RunState` transition → objective event → queued evidence flush → owned single-use run completion. Before the transaction, the Route Handler reloads the owned run and ordered event rows, rejects unknown configured IDs or duplicates, requires the world objective to be the final event, enforces the configured timer and a conservative configuration-derived traversal minimum, and rejects stale/future runs. PostgreSQL then derives coins and score from unique recorded events plus the bounded world duration; the browser no longer submits score, coin totals, completion flags, world reached, or a user ID. The transaction advances sequential progression, awards the relevant compass/treasure badge, and inserts a leaderboard row only for World 3. A modified client can still fabricate a plausible sequence of valid collision IDs because this is a browser game, so rankings are integrity-checked rather than cheat-proof. It cannot submit arbitrary numeric totals, duplicate one entity within a run, complete a locked world, reuse a submitted run, or write tables directly. Server simulation or signed deterministic replay was considered stronger but disproportionate to the current Arcade Physics client.

The former `/api/progress` PATCH was removed after this transaction became the sole authenticated completion path; `/api/progress` remains a read-only projection. This avoids retaining a second client-declared world-completion route beside verified runs.

Achievement state has one source for authenticated players: `player_progress` owns aggregate gem/fish counts and `achievements` owns unique badges. Event insertion and threshold award happen in the same row-locked transaction, so React notifications are presentation of newly returned keys rather than reward authority. `lib/game/achievements.js` contains display metadata and the equivalent temporary guest thresholds; it has no Supabase or Phaser dependency. Procedural gem and compass textures stay in the render boundary, while coordinates remain level configuration.

Rankings are one best completed World 3 run per registered player. The service-role-only ranking function uses deterministic score, duration, and completion-time ordering, returns the top ten plus the requesting player's row, and never exposes user IDs. The profile and leaderboard remain server-loaded DTOs; sign out continues through the existing auth Route Handler. Fish revival is unchanged and can pause/resume the same issued run without entering achievement or ranking modules.

## JavaScript project resolution

The workspace uses TypeScript 6.0.3 as the JavaScript language service. TS5101 reported that `baseUrl` is deprecated for TypeScript 7. The supported configuration removes `baseUrl` and retains `paths: { "@/*": ["./*"] }`; TypeScript 6 resolves those targets relative to `jsconfig.json`. This preserves all aliases without suppressing deprecations, adding a bundler setting, or migrating JavaScript to TypeScript.

The observed Windows `.next` `EPERM` failure was caused by the managed filesystem sandbox rather than Next worker concurrency. The project keeps Next's default worker configuration; production verification runs outside that sandbox when required.

## Phase 9 audio boundary

`AudioController` is the single application-lifetime owner for browser audio. It maps the current route to one original procedural soundtrack, installs the user-interaction unlock required by browser autoplay policy, and destroys its context/listeners on unmount. `audio-service.js` owns the Web Audio context, eight-beat layered loop scheduling, oscillator cleanup, independent music/effect switches, master volume, gentle output compression, and versioned local persistence. Route changes stop the previous loop before starting another, so screens never create competing players.

Phaser remains audio-independent. Existing serialisable collection, `player:damaged`, `run:revived` and run-ended bridge events let `GameScreen` request focused effects; enemy contact, thorns and falls converge on the same damage event and therefore the same cue. The React-owned resume state plays one guarded pulse for each 3→2→1→GO step during normal and revival countdowns. No physics or Fish module imports Web Audio. Pause state crosses through the existing snapshot and suspends soundtrack scheduling, while the normal resume command restarts it. Reduced-motion media queries and scene checks remain unchanged because motion accessibility is an operating-system concern, not an audio preference.

## Phase 6 UI orchestration

`GameScreen` remains the React coordinator for accessible overlays and serialisable bridge commands; it never receives a Phaser scene or body. `HowToPlay` owns factual control/mechanic presentation and is reused by the pre-run briefing and About overlay. `game-flow.js` contains only pure UI transition policy: World 1 introduction eligibility, the fixed resume sequence and next-world lookup. World/physics rules remain in configuration and Phaser systems rather than being copied into UI.

The World 1 introduction is a true lifecycle gate: `GameScreen` does not subscribe/construct Phaser until Start Adventure changes `started`. Pause ordering is Arcade pause and `CombatState.pause` → state snapshot → React overlay → 3–2–1–GO timeouts → one `game:resume` command → Arcade/combat resume. Each timeout cleans up on state change or unmount, repeated Resume clicks are hidden/guarded, Escape cannot bypass the countdown, and restart resumes the paused physics plugin before rebuilding the scene. Polling Phaser from React or running a second UI timer inside the scene were rejected because either would couple lifecycles or create two run clocks.

Checkpoint ordering is collision overlap → guarded `RunState.complete` → `world:completed` → guest-memory update or authenticated Route Handler → saved/error UI state. Next World is enabled only after `saved`; authenticated failure offers Retry Save and cannot claim an unlock. The final treasure has no next-world branch. `getPlayerAchievements` extends the existing repository DTO boundary, while the profile receives server-loaded profile/progress/achievement data and the leaderboard continues using its authorised projection. A client global store or direct Supabase queries from panels would add coupling without improving these route-scoped flows.

The Fish adapter is unchanged and absent from the briefing, pause and navigation dependency graph. The local fish description reflects implemented eight-second combat only. Challenge attempts, achievements and revival UI remain planned, so provider failure cannot affect the new UX. Identity remains Supabase SSR claims plus RLS and server-authorised mutations; guest memory never enters profile/leaderboard data. Profile achievement empty states are explicit rather than synthesized, and leaderboard rows remain server data despite the documented client-originated numeric-score limitation.

### Phase 6 final correction and leaderboard audit

`GameScreen` still owns pause presentation, but the resume sequence is now a transparent `resume-canvas-layer` over the live canvas rather than a second card/modal. Phaser remains paused for every 3–2–1–GO state; the React timeout effect emits exactly one existing `game:resume` command after GO and clears its timeout on restart or unmount. The full-size layer intercepts touch input during the countdown while keeping the canvas and HUD visible. Moving the countdown into Phaser would reduce React markup but duplicate accessibility/navigation work and introduce another scene timer.

Backdrop composition is isolated in the pure `getBackdropCoverLayout` function. `WorldScene.resizeBackdrop` supplies the real source and camera-viewport dimensions; only Crystal Cavern requests a 1.12 centred overscan because its 2:1 panorama exposes a painted dark edge on wider displays, unlike the 3:1 World 1/2 panoramas. The cover calculation preserves source aspect ratio and changes neither camera bounds nor collision geometry. Per-viewport hand-tuned offsets were rejected because they would be brittle and could reintroduce gutters at new sizes.

The leaderboard read path is `WorldsPage` → verified Supabase claims → `getLeaderboard` → RLS-authorised `leaderboard_entries` projection → `LeaderboardPanel`. Independent `Promise.allSettled` results prevent an unrelated profile/achievement query failure from discarding valid leaderboard rows, and a failed leaderboard query now renders “Rankings unavailable” instead of a false empty ranking. The write path exists separately as `/api/runs/start` and `/api/runs/[runId]/complete`; both derive ownership from verified claims, and the latter calls the service-role-only single-use SQL function. Gameplay currently calls only `/api/progress`, so registration, login and World 3 progress cannot create a ranking. A read-only project audit found three profiles, one completed-World-3 progress row, zero issued runs and zero submitted runs; therefore no legitimate entry can exist through the current flow. Wiring server-issued run lifecycle/evidence is deliberately deferred to a ranked-run security phase rather than trusting the Phaser score or fabricating a row.

The Fish adapter remains outside UI, rendering and leaderboard dependencies: it continues to normalise the real upstream contract, validate safe images, enforce HTTPS/timeouts and fail without blocking gameplay. Supabase SSR cookies, RLS, least-privilege grants and temporary guest memory are unchanged. A direct client leaderboard insert or Fish request would be simpler superficially, but would expose external formats and weaken ownership/score controls.

### Phase 6 final shrine, celebration and balance pass

High cohesion remains configuration-driven. The three level files now own longer collision layouts, optional `riskRoute` coin metadata, three local fish positions, and grounded enemy/hazard placement; `WorldScene` still owns the one implementation of loading, physics, collection, combat and completion. `RunState` remains the only score/duplicate guard, while `CombatState.activate` retains the explicit refresh-to-eight-seconds rule. The analytical no-obstacle traversal lower bounds are about 17.8, 18.2 and 19.7 seconds; these are geometry comparisons, not claimed playthrough times. A copied scene or new balancing manager would duplicate existing contracts, while dynamic procedural generation would make assessment and fairness harder to reproduce.

Checkpoint remains the internal goal/progression value because SQL and existing bridge consumers rely on that stable contract. `WorldScene.createGoal` and React presentation translate it to the player-facing Compass Shrine concept. Goal overlap follows guarded `RunState.complete` → physics pause → scene-owned celebration → final snapshot → `world:completed` → guest memory or verified progress Route Handler. The same status guard prevents duplicate shrine/treasure transitions. Magical light, petals and sparkles are bounded Phaser objects tracked in `effectObjects`; completion destroys transient objects and scene shutdown kills their tweens. Reduced-motion users receive static illumination without camera flash or moving particles.

Competitive rewards remain understandable: coins are 100 points, unique enemies 250, and remaining seconds 10 each. The theoretical per-world maxima from configured coins/enemies/time are 6,700, 6,900 and 7,650, so optional upper routes and combat matter more than simply sprinting, while later worlds retain the higher ceiling. These browser-computed scores are still not authoritative evidence; gameplay does not call the ranked-run endpoints and no arbitrary score acceptance was added.

Authentication forms remain clients of focused email/password Auth Route Handlers. Labels, validation associations, disabled/pending states and password visibility are presentation concerns; Supabase SSR claims, cookies, RLS and server-derived identity remain the authorization boundary. The Fish adapter also remains independent: Compass Shrines expose no challenge result and do not import `lib/fish`. A later optional challenge can subscribe after durable shrine progression without becoming a prerequisite for unlocking the next world.

### Focused UI and physics correction

Contact damage and fall recovery now have separate scene responses. `RunState.damage` remains the single life/invulnerability guard: enemy and thorn contact publishes one damage event, applies short knockback and leaves the live scene state and position intact. The shared scene records grounded, hazard-clear positions through the existing platform collider; only a real fall restores the most recent verified position. A fall during an existing invulnerability window restores safely without charging a second life. Zero lives still follows the unchanged Game Over event path.

The shared motion configuration uses a measured 750 px/s jump impulse with the existing 1,500 px/s² gravity, while `PlayerController` accepts both current collision contact and Arcade's resolved downward block as grounded. Hunter body dimensions retain the measured opaque boot baseline. Camera zoom remains height-derived but now supports normal high-resolution viewports, uses a viewport-relative deadzone on narrow screens, and supplies the resulting camera viewport to aspect-preserving backdrop cover with a two-pixel bleed. Canvas CSS no longer requests replaced-element stretching.

Selected-world preloading remains isolated in `game/preload-gameplay.js`. The World Map still speculatively warms only the selected unlocked world, but Play now awaits that same deduplicated promise before client navigation and exposes a real preparing/error state. `GameScreen` continues to require Phaser's loader and `game:ready` event; no asset, route, or readiness state is fabricated, and the other two worlds are not preloaded.

Remote flows are asynchronous events at the application boundary. A checkpoint or Game Over screen requests a challenge from a Route Handler; the server obtains and validates an upstream response, stores the solution with ownership and single-use metadata, and returns only the challenge image and local challenge ID. Answer validation and any bonus/revive mutation happen atomically on the server.

### Phase 7 Fish revival

Fish revival is available only after a zero-life Game Over. `GameScreen` creates one opaque run-attempt UUID, while ownership comes independently from verified Supabase claims (`auth:<uuid>`) or a signed, HttpOnly guest virtual-identity cookie (`guest:<uuid>`). Opening the panel immediately starts one guarded request; the component-level ref prevents React development-effect replay from creating a second Guest identity or challenge. The server calls `fish-service.js`, persists only the upstream `fish` solution in `fish_challenges`, and returns the local challenge ID plus a base64 PNG data URL. Base64 mode prevents the provider's count-bearing filename from leaking into browser state. There is no player answer deadline; the legacy required `expires_at` column receives a non-expiring compatibility value. The record remains bound to owner, run attempt and world. Guest identity never enters profile, progress, run or leaderboard tables.

Answer submission calls the service-role-only `verify_fish_challenge_admin` function. Its row lock, per-challenge attempt cap, consumed timestamp and partial unique index atomically enforce one successful challenge per owner/run, including concurrent or repeated requests. An incorrect result closes the panel without consuming the run's revival; reopening requests a fresh puzzle. Challenge and answer routes allow twenty requests per five-minute IP window, preserving abuse protection without blocking ordinary retries, and report the server retry delay when that limit is genuinely reached. The provider solution is absent from DTOs, React state, bridge events and logs. Provider or database failure leaves Play Again and World Map available and cannot change progression.

After a successful server response, React emits only `game:revive`. `RunState.revive` is the second guard: it accepts only a zero-life terminal state and at most `RUN_RULES.maxFishRevives`. `WorldScene` restores the verified hazard-clear ground position, grants exactly one life, keeps physics and the active game clock paused, and publishes `run:revived`. React then shows the existing 3–2–1–GO canvas overlay and emits the normal resume command only after GO; score, collected sets, defeated enemies, timer and combat clock remain in the same scene. The normal scene shutdown still owns every bridge unsubscribe, so remounts cannot retain a revival listener.

## Fish Game API verification

Verified on 4 November 2026 against the provider documentation and live service:

- Documentation: `https://marcconrad.com/uob/fish/doc.php` (page updated June 2026).
- Documented base URL: `http://marcconrad.com/uob/fish/api.php`; HTTPS at `https://marcconrad.com/uob/fish/api.php` also returned HTTP 200 and is the configured default to avoid mixed content.
- Optional query parameters: `out=json|csv` (default `json`) and `base64=yes|no` (default `no`).
- Observed URL JSON response: `{ "question": "https://www.sanfoh.com/uob/fish/data/...png", "fish": 9, "chest": 1 }`.
- Observed base64 JSON uses the same keys with `question` containing raw PNG base64 text.
- Observed CSV is `question,fish,chest`; `question` is a URL or raw base64 depending on the switch.
- Responses reported `Content-Type: text/html`, even for JSON, so the adapter parses text explicitly and validates every field.
- Four live variants returned HTTP 200 in about 0.7-1.1 seconds during the check. This is a point-in-time connectivity result, not an uptime guarantee.
- Provider terms say the service is supplied as-is, may be discontinued without notice, and must not be used commercially.

The meaning and permitted ranges of `fish` and `chest` are not specified on the documentation page. The adapter therefore preserves them as validated non-negative integers without inventing additional semantics. Gameplay integration will be confirmed against the provider’s example UI before the challenge screen is finalized. Server requests use an abort timeout and validate the observed HTTPS image host/path or PNG base64 data. Future challenge routes must avoid logging solutions and degrade to a skippable unavailable state.

## Phase 2B identity and persistence

`proxy.js` and `lib/supabase/proxy.js` refresh Supabase SSR cookies with `getClaims()`. Browser and server client construction remains isolated in `lib/supabase/`; the server-only secret client is created only for narrowly scoped trusted operations. Route Handlers call `lib/auth/session.js` and derive the player ID from verified claims, never from a request body.

Email registration, password login and logout are Route Handlers under `app/api/auth/`. Registration requires the normal Supabase session returned when Confirm email is disabled; passwords remain exclusively managed by Supabase Auth. Responses use no-store headers and focused public-error mapping. A bounded per-instance request guard supplements Supabase Auth provider limits; production must also configure provider/dashboard limits because an in-memory limiter is not distributed across Vercel instances.

The migration creates `profiles`, `player_progress`, `achievements`, `game_runs`, and a denormalised safe `leaderboard_entries` projection. RLS restricts private rows to `auth.uid()`. Direct player writes to progression, achievements, and runs are revoked. Because automatic table exposure is disabled, `service_role` receives only the table operations used by the server adapters: profile lookup, progress read/update, run read/insert/update, and leaderboard insert. It receives no achievement or identity-sequence access. Trigger functions are not directly executable by API roles.

Server Route Handlers validate bounds and call service-role-only database functions for sequential world completion and single-use run submission. A completed leaderboard submission must identify World 3 and the locked progress row must already record all three worlds complete; earlier-world, out-of-order, foreign, and repeated submissions are rejected. The secret key never enters a client bundle.

Guest progress is memory-only and is ignored by authenticated pages. Guests cannot read or submit leaderboard data. Registered progress remains PostgreSQL-backed across refresh/logout/login and the UI consumes stable profile/progress/leaderboard shapes from `lib/data/player-repository.js`, not database internals.

Fully authoritative score calculation is impossible while Phaser executes in the browser. The server does not blindly accept a user ID or completion flag: it derives identity from verified claims and cross-checks the owned server-issued run, numeric bounds, unlocked progression, persistent World 3 completion, and single submission in one transaction. The numeric score remains client-originated; Phase 3 must connect trusted gameplay evidence or server-recomputable scoring before treating it as cheat-proof.

## Phase 2A interface boundary

App Router pages compose reusable presentation components from `components/ui`, `components/auth`, `components/overlays`, and `components/worlds`. Pure form rules live in `lib/validation` so validation is testable without coupling it to Supabase. Login and registration stop after local validation and state clearly that no request or account mutation occurred.

Welcome is the single main menu. Settings and About use accessible in-place dialogs instead of separate information pages. Guest play opens the World Map directly and reads temporary sequential completion state through `lib/progress/guest-progress.js`; gameplay calls its completion function. Authenticated persistence uses the Phase 2B session boundary.
