# Assessment code evidence

This maps the actual source to the rubric and distinguishes implemented evidence from planned gameplay.

## 1. High cohesion, low coupling, and encapsulation

**Implemented files:** `components/auth/`, `lib/auth/`, `lib/data/player-repository.js`, `lib/supabase/`, `lib/progress/guest-progress.js`, `game/config/`, `game/scenes/world-scene.js`, `game/systems/`, `game/core/input-state.js`, `game/core/combat-state.js`, `game/core/run-state.js`, `game/core/collision-rules.js`, and `game/render/`.

**Evidence and justification:** pages compose focused screens; pure validation does not import React or Supabase; session verification, redirect safety, error mapping, HTTP responses, and database queries are separate modules with small function APIs. The World Map receives profile/progress/leaderboard models instead of querying services, while the guest hook owns only an in-memory subscription. Shared world rules remain configuration, so React and Phaser scenes do not copy them. This creates focused reasons to change and permits unit tests without a browser or database.

**Alternative:** a single page/server action could validate, authenticate, query, and render with fewer files. It would be faster initially, but UI changes would be coupled to identity and persistence, tests would need more infrastructure, and Phaser reuse would be harder. A class/repository hierarchy was also rejected because it adds abstraction without multiple implementations.

Phase 3A extends this separation: `WorldScene` coordinates Phaser lifecycle and collisions, `PlayerController` translates keyboard/touch commands into movement, `EnemySystem` owns patrol and teardown, `RunState` owns deterministic score/lives/timer rules, and the Emerald Jungle layout is configuration data. React does not import these internal systems; it dynamically loads only the game factory.

**Phase 3B critical discussion:** the early scene mixed movement assumptions, combat timing, camera resize and asset creation. The implemented refactor extracts cohesive contracts: `InputState` owns source-aware controls; `CombatState` owns power/cooldown transitions; `ProjectileSystem` owns projectile bodies and overlap; `CameraController` owns resize/follow cleanup; `collision-rules` owns the reusable stomp decision; and render modules own URLs, animations and measured atlas alignment. `WorldScene` still coordinates these pieces because Phaser collision registration is a legitimate scene lifecycle responsibility. The post-phase review removed `physics-model.js`: only tests imported it, so test-local jump calculations are clearer than a false production abstraction. Extracting every callback into a service or adding an entity framework was rejected because it would scatter Phaser's lifecycle without independent reuse.

**Runtime correction evidence:** `.next/dev/logs/next-development.log` identified `Sprite.setAllowGravity` as the initialization exception. `WorldScene.createPlayer` and respawn now call the actual `Phaser.Physics.Arcade.Body` method. This keeps display concerns on the sprite and physics state on its body instead of wrapping Phaser behind an unnecessary adapter.

**Phase 4 evidence:** `sunset-ruins.js` implements World 2 entirely as data; `levels.js` is a two-entry lookup; `load-assets.js` and `getTerrainVisualLayout` accept the selected art contract; `EnemySystem` receives only presentation measurements. The same `WorldScene`, controllers, combat rules, HUD and progression path run both worlds. Separate scenes or subclasses were rejected because biome differences are data, while a generic entity framework would add concepts with no current reuse. World 3 and audio remain incomplete, and authoritative run evidence is still required before scores can be called cheat-proof.

**Phase 4 physics correction:** responsibility remains narrow: world files own platform rectangles and patrol ranges; `create-textures.js` owns atlas cropping and painted-surface measurements; `collision-rules.js` owns pure contact/fall predicates; `PlayerController` owns grounded input; `WorldScene` coordinates Phaser bodies and run transitions. Measured crops remove transparent atlas padding without moving physics into rendering, while `surfaceWidthRatio` makes the visible walkable span equal the configured collider. The correction changed shared data/contracts rather than branching by world. A tilemap or per-world scene could encode geometry visually, but would require an asset rewrite or duplicate mechanics; a universal entity/physics manager would obscure Phaser's already adequate lifecycle.

**Navigation optimisation:** `WorldMap` owns selection and route intent; `preload-gameplay.js` owns only runtime/image warming and request deduplication; `GameScreen` owns one mounted Phaser instance and the fallback UI; `WorldScene` remains the authority for actual asset readiness. Their interfaces are a world ID, a game-factory module and serialisable bridge events. Phaser is still dynamically split from the map bundle. A persistent global game or store could avoid construction, but would couple routes to GPU/input/run state and make replay cleanup harder; preloading all worlds at Splash would add unnecessary startup bandwidth.

## 2. Event-driven programming and handlers

**Implemented files:** `game/core/events.js`, `game/core/game-bridge.js`, `game/core/input-state.js`, `game/core/combat-state.js`, `components/game/game-screen.js`, `components/game/mobile-controls.js`, `game/scenes/world-scene.js`, `game/systems/player-controller.js`, `game/systems/projectile-system.js`, and tests.

**Evidence and justification:** submit/click/change handlers perform one UI responsibility and call narrow helpers. Timers, Escape listeners, animation frames, and guest progress listeners are removed during cleanup. The guest subscription exposes completed IDs rather than internal mutable state. `game/core/events.js` defines serialisable React/Phaser event names so neither side needs the other's internal objects.

**Alternative:** a global event bus for every UI action would reduce prop callbacks but obscure control flow and listener ownership. Directly passing Phaser scenes into React would be convenient but couple two lifecycles and make teardown/testing fragile.

Phase 3A now implements the bridge. React publishes small command payloads; Phaser collision, overlap, timer, and lifecycle handlers publish serialisable state or terminal events. Every `on` call returns an unsubscribe function; `GameScreen`, `PlayerController`, `WorldScene`, and the Phaser game all release listeners/resources during cleanup. `RunState` ignores mutations outside the running state, preventing duplicate completion or Game Over transitions.

**Phase 3B critical discussion:** actual event sources are keyboard/touch input, Arcade collider/overlap callbacks, scene update/timer transitions, Escape, scale resize and scene shutdown. Commands are `input:changed`, `input:release-all`, `game:pause`, `game:resume` and `game:restart`. Domain events include `coin:collected`, `fish:collected`, `power:started`, `power:expired`, `projectile:fired`, `enemy:stomped`, `enemy:defeated`, `player:damaged`, `state:changed`, `world:completed` and `run:ended`. Fish ordering is overlap -> activate rule state -> domain events -> snapshot; completion transitions state before emitting persistence work. Disabled bodies plus `RunState` sets prevent duplicate coin/enemy/completion effects. Bridge subscribers return ownership-specific unsubscribe functions. Scene cleanup removes bridge, keyboard, resize and collider listeners; Phaser disposes groups. A single global bus for React, Phaser and services was rejected because it would hide ownership and allow backend concerns into moment-to-moment gameplay. Direct React callbacks were rejected because they would expose scene objects and couple lifecycles.

**Current correction:** guest progression is not persistent. Welcome emits a reset before client navigation; World Map subscribes to module-memory changes; completion publishes once; unsubscribe removes ownership when the map unmounts. An attempt query value makes repeated game entries distinct and reconstructs `GameScreen`, Phaser and `RunState` without a run manager. Phaser platform collision remains scene-owned, while the pure `canLandOnPlatform` predicate contains only the reusable descending-from-above rule. Session storage was rejected because refresh must reset; React context/global state libraries were rejected as unnecessary.

**Remaining:** local fish power/projectile events are implemented. External checkpoint challenge, achievement and revive events are **planned**, not claimed as implemented.

**Phase 4 evidence:** the World 2 checkpoint is another Arcade overlap source and follows the existing order: guarded `RunState.complete` -> physics pause and final snapshot -> `world:completed` -> React guest or authenticated progression handler. The handler uses `world.number`, so it unlocks World 3 without a World-2-specific callback. Restart emits `game:restart` and recreates the selected level; cleanup ownership is unchanged. Polling the scene from React was rejected because it would duplicate state and miss exact transition edges; direct persistence inside the collision callback was rejected because network lifecycle does not belong to Phaser.

**Phase 4 physics correction:** Arcade produces collision/contact state; the one-way process callback accepts only descending contact from above; losing `blocked.down` immediately returns control to gravity. Crossing the fall boundary invokes `damagePlayer` once per fall, `RunState.damage` guards life/terminal transitions, and `body.reset` synchronises current/previous body state before the next frame. Completion and Game Over remain mutually guarded terminal events. Scene shutdown still removes command, keyboard and collider ownership. Polling positions from React or directly calling persistence from a fall/collision callback would couple lifecycles and add ordering races.

**Navigation optimisation:** selection changes trigger two independent speculative events: `router.prefetch` warms the dynamic route and `preloadWorld` warms only its runtime/textures. Neither declares success. On mount, `GameScreen` subscribes before boot; Phaser loader failure emits `game:load-failed`, while successful scene creation emits `game:ready` and the first `state:changed`. Cleanup marks the async boot inactive, removes window and bridge subscriptions, destroys the single game and prevents late promise resolution from creating another instance. Polling canvas children or using a fixed delay would be simpler but cannot establish real readiness and can produce blank/stale screens.

**Verified runtime evidence:** the production build launched warmed World 1 and World 2 in about 0.77–0.81 seconds with `status=loading` briefly observable, one canvas, and no visible loading overlay; readiness then changed to `playing`. Map return removed all canvases and replay reset score/coins/lives/timer. Desktop 1440×900 and mobile 320×568 had no document scrolling or console errors. Real World 1 completion unlocked World 2; walking unsupported gaps in both worlds removed one life and respawned the player. These checks do not substitute for configured Supabase/OAuth/RLS verification.

## 3. Third-party interoperability

**Implemented files:** `lib/fish/fish-service.js`, `tests/fish-service.test.js`, `lib/supabase/*`, auth/progress/run Route Handlers, and the SQL migration.

**Evidence and justification:** the Fish adapter is an anti-corruption layer: it owns URL construction, timeout, text parsing for the provider's inaccurate content type, schema/image validation, and stable errors. It accepts injected fetch for isolated tests, and React never imports the upstream `{ question, fish, chest }` response. Supabase transport/cookies are similarly isolated; UI calls stable application routes/models instead of Auth or PostgREST response shapes.

**Phase 3B critical discussion:** the in-level fish is intentionally only local domain data in `emerald-jungle.js` and `CombatState`; it imports no HTTP adapter and its outage-free eight-second behavior cannot be affected by the university service. The remote adapter remains server-oriented, HTTPS-only for observed images, timeout-protected, schema-normalised and fetch-injectable. This demonstrates two meanings of “fish” without coupling them. Calling the Fish API directly from Phaser was rejected because it would expose upstream formats/solutions, tie physics progress to network latency and make scene cleanup own HTTP cancellation. A generic plugin framework was rejected because one unstable API is clearer behind one explicit anti-corruption layer.

**Post-phase review:** no Fish adapter change was required. Sprite grounding and replay construction depend only on render/run modules, so the remote service remains unable to affect local combat or progression.

**Current correction:** Fish adapter code and contracts are unchanged. Guest-memory events and platform process callbacks have no import path to `lib/fish`, so local shooting and ordinary progression remain available during provider failure.

**Alternative:** React could call Fish/Supabase directly. That would reduce server code, but expose Fish solutions, spread third-party formats through UI, weaken identity checks, and make provider outages screen concerns. A generic integration framework was rejected as unnecessary for two explicit adapters.

**Remaining:** Fish attempt storage, answer verification, achievements, and revive routes/UI are **planned**. The optional service must never block normal progression. Live Supabase interoperability also requires the owner's environment configuration.

**Phase 4 evidence:** `sunset-ruins.js` contains a local fish coordinate only. Collection still enters `CombatState` and `ProjectileSystem`; neither imports `fish-service.js`. The remote adapter remains an HTTPS server-side anti-corruption layer with injected fetch, abort timeout, explicit text-to-JSON parsing, image allow-listing and normalized errors. Direct browser calls would expose provider formats and solutions and couple play to availability; a generic integration SDK would be excessive for one documented HTTP endpoint. External challenge UI and answer persistence remain planned, not represented by the local collectible.

**Phase 4 physics correction:** no Fish integration code changed or enters the terrain/fall dependency graph. `lib/fish/fish-service.js` remains the independently tested server-side adapter for the provider's real HTTP/JSON contract, while local fish collection remains deterministic `CombatState` data. This isolation means an API timeout cannot alter collision, lives, checkpoint progression or the eight-second local power. Direct Phaser HTTP calls remain the rejected alternative because they expose provider schema/solutions and couple play to availability.

**Navigation optimisation:** the preload manifest is built only from local game art configuration and has no Fish adapter import. The optional Fish service remains server-side, validates the provider's unusual text/JSON response and safe image forms, uses timeout/abort handling and normalised errors, and cannot delay route or scene readiness. Preloading remote challenges would waste requests, expose upstream timing to gameplay startup and violate optional failure isolation; challenge UI remains planned.

## 4. Virtual identity, cookies, and authorization

**Implemented files:** `proxy.js`, `lib/supabase/proxy.js`, `lib/auth/session.js`, `lib/auth/redirects.js`, `app/api/auth/*`, `app/auth/callback/route.js`, `app/auth/confirm/route.js`, `components/profile/profile-panel.js`, `.env.example`, and `supabase/migrations/202611050001_phase_2b_auth_and_progress.sql`.

**Evidence and justification:** `@supabase/ssr` refreshes cookie sessions at the Next.js proxy boundary; protected routes call `getClaims()` and use the verified `sub`, never a submitted user ID. OAuth uses PKCE code exchange, email confirmation exchanges a short-lived token hash with `verifyOtp`, and both use allow-listed local return paths. Public and secret keys have separate factories. RLS limits private selects/updates to `auth.uid()`, while direct progression/run writes are revoked. The RLS-bypassing service role has explicit operation-level grants only for current server work and no unused achievement/sequence access. Trusted mutations are atomic functions reached only after server identity and input checks; leaderboard insertion additionally requires an owned, single-use run, World 3 declaration, and persistent completion of all three worlds. Logout remains inside the authenticated profile panel. Guests use separate temporary memory and cannot submit leaderboard runs.

**Alternative:** custom password hashes/session tables provide control but add credential, recovery, OAuth, rotation, and cookie-security responsibilities. Client-only local-storage tokens are simpler but script-readable and unsuitable as a server authorization source. Supabase SSR plus RLS was selected for managed identity and layered authorization.

**Remaining and limitations:** email delivery, Google consent, live cookie refresh, and RLS cross-user denial require a configured Supabase project. The in-memory request guard is a best-effort application layer; distributed production limits must use Supabase/platform controls. Score values still originate in client-side Phaser and therefore cannot be fully cheat-proof. Phase 3 must provide trusted gameplay evidence or a server-recomputable score; current checks validate identity, ownership, bounds, progression, World 3 completion, and one-time submission without claiming authoritative scoring.

Authenticated World 1 completion calls `/api/progress` without submitting a leaderboard score; the Route Handler still derives identity from verified claims. Guest completion uses only the in-memory adventure service. This preserves the identity boundary while the later authoritative score design remains explicitly unfinished.

**Phase 3B critical discussion:** gameplay receives only a mode flag and stable progress result. On `world:completed`, guests update memory only; authenticated players call `/api/progress` without sending a user ID. The Route Handler verifies SSR cookie claims and the database function/RLS enforce sequential ownership. Phaser never imports Supabase, cookies or profile data. Keeping guests as anonymous Supabase users was rejected because it would mix guest and account identities and expand RLS/session complexity. Custom session cookies were rejected in favour of Supabase PKCE/SSR refresh because custom credential storage, rotation and OAuth linking add security risk. Configured email/OAuth and deployed RLS remain owner-environment checks, not falsely claimed here.

**Current identity boundary:** guest reset cannot delete or overwrite registered data because it removes only `treasurehunt.guest-progress.v1` and mutates one browser-memory array. Authenticated World Map state still comes from `getPlayerProgress` using the verified cookie identity, and completion still reaches the service-role function only after Route Handler verification. Unit tests prove guest transitions do not mutate supplied authenticated progress. Live persistence across logout/login still requires the configured Supabase project and is not claimed as locally exercised.

**Phase 4 evidence:** `app/game/[worldId]/page.js` authorizes authenticated World 2 from server-loaded `completed_worlds`; `GameScreen` independently guards guest World 2 from ordered in-memory state before Phaser boots. Authenticated completion submits no user ID: `/api/progress` uses `getClaims()`, bounded validation and the service-role-only sequential SQL function behind RLS and least-privilege grants. Registration success reports confirmation-required state but does not create a client session or bypass email verification; password values are cleared. Custom session cookies or anonymous Supabase guests would add credential/RLS responsibilities and blur identities. Live email delivery, OAuth consent, cookie persistence and deployed RLS denial remain owner-environment verification items.

**Phase 4 physics correction:** gameplay geometry remains identity-agnostic. Guest completion still mutates only the active in-memory adventure; authenticated completion still crosses `/api/progress`, which derives `sub` from verified Supabase SSR claims and relies on RLS/service-role-only sequential mutation. No client-supplied user ID or collision outcome was added. Supabase anonymous users or custom cookies could persist guest identity, but would violate the required temporary guest boundary and add session/RLS responsibility. Live provider, cookie and cross-user RLS checks remain configuration-dependent rather than claimed by local physics tests.

**Navigation optimisation:** route prefetch follows the same guest/authenticated URL. It does not cache or invent identity: the authenticated game page still verifies Supabase SSR claims and loads authorised progress server-side, while guest access still checks the active in-memory sequence before Phaser boots. Asset/runtime promises contain no profile, cookie or progression data. Making the game route purely client-authorised would be faster but would weaken server identity and locked-world checks; anonymous Supabase users would blur the intentionally temporary guest boundary.
