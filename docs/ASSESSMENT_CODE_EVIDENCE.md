# Assessment code evidence

This maps the actual source to the rubric and distinguishes implemented evidence from planned gameplay.

## 1. High cohesion, low coupling, and encapsulation

**Implemented files:** `components/auth/`, `lib/auth/`, `lib/data/player-repository.js`, `lib/supabase/`, `lib/progress/guest-progress.js`, `game/config/`, `game/scenes/world-scene.js`, `game/systems/`, `game/core/input-state.js`, `game/core/combat-state.js`, `game/core/run-state.js`, `game/core/collision-rules.js`, and `game/render/`.

**Evidence and justification:** pages compose focused screens; pure validation does not import React or Supabase; session verification, redirect safety, error mapping, HTTP responses, and database queries are separate modules with small function APIs. The World Map receives profile/progress/leaderboard models instead of querying services, while the guest hook owns only an in-memory subscription. Shared world rules remain configuration, so React and Phaser scenes do not copy them. This creates focused reasons to change and permits unit tests without a browser or database.

**Alternative:** a single page/server action could validate, authenticate, query, and render with fewer files. It would be faster initially, but UI changes would be coupled to identity and persistence, tests would need more infrastructure, and Phaser reuse would be harder. A class/repository hierarchy was also rejected because it adds abstraction without multiple implementations.

Phase 3A extends this separation: `WorldScene` coordinates Phaser lifecycle and collisions, `PlayerController` translates keyboard/touch commands into movement, `EnemySystem` owns patrol and teardown, `RunState` owns deterministic score/lives/timer rules, and the Emerald Jungle layout is configuration data. React does not import these internal systems; it dynamically loads only the game factory.

**Phase 3B critical discussion:** the early scene mixed movement assumptions, combat timing, camera resize and asset creation. The implemented refactor extracts cohesive contracts: `InputState` owns source-aware controls; `CombatState` owns power/cooldown transitions; `ProjectileSystem` owns projectile bodies and overlap; `CameraController` owns resize/follow cleanup; `collision-rules` owns the reusable stomp decision; and render modules own URLs, animations and measured atlas alignment. `WorldScene` still coordinates these pieces because Phaser collision registration is a legitimate scene lifecycle responsibility. The post-phase review removed `physics-model.js`: only tests imported it, so test-local jump calculations are clearer than a false production abstraction. Extracting every callback into a service or adding an entity framework was rejected because it would scatter Phaser's lifecycle without independent reuse.

**Runtime correction evidence:** `.next/dev/logs/next-development.log` identified `Sprite.setAllowGravity` as the initialization exception. `WorldScene.createPlayer` and respawn now call the actual `Phaser.Physics.Arcade.Body` method. This keeps display concerns on the sprite and physics state on its body instead of wrapping Phaser behind an unnecessary adapter.

**Phase 4 evidence:** `sunset-ruins.js` implements World 2 entirely as data; `levels.js` is a two-entry lookup; `load-assets.js` and `getTerrainVisualLayout` accept the selected art contract; `EnemySystem` receives only presentation measurements. The same `WorldScene`, controllers, combat rules, HUD and progression path run both worlds. Separate scenes or subclasses were rejected because biome differences are data, while a generic entity framework would add concepts with no current reuse. World 3 and audio remain incomplete, and authoritative run evidence is still required before scores can be called cheat-proof.

**Phase 4 physics correction:** responsibility remains narrow: world files own platform rectangles and patrol ranges; `create-textures.js` owns atlas cropping and painted-surface measurements; `collision-rules.js` owns pure contact/fall predicates; `PlayerController` owns grounded input; `WorldScene` coordinates Phaser bodies and run transitions. Measured crops remove transparent atlas padding without moving physics into rendering, while `surfaceWidthRatio` makes the visible walkable span equal the configured collider. The correction changed shared data/contracts rather than branching by world. A tilemap or per-world scene could encode geometry visually, but would require an asset rewrite or duplicate mechanics; a universal entity/physics manager would obscure Phaser's already adequate lifecycle.

**Navigation optimisation:** `WorldMap` owns selection and route intent; `preload-gameplay.js` owns only runtime/image warming and request deduplication; `GameScreen` owns one mounted Phaser instance and the fallback UI; `WorldScene` remains the authority for actual asset readiness. Their interfaces are a world ID, a game-factory module and serialisable bridge events. Phaser is still dynamically split from the map bundle. A persistent global game or store could avoid construction, but would couple routes to GPU/input/run state and make replay cleanup harder; preloading all worlds at Splash would add unnecessary startup bandwidth.

**Phase 5 evidence:** `crystal-cavern.js` owns only final-level data and measured art presentation; `levels.js` exposes the same lookup; `WorldScene.createGoal` consumes the narrow `{ type, x, y }` contract; existing `PlayerController`, `EnemySystem`, `CombatState`, `ProjectileSystem`, `RunState`, render and camera modules are unchanged in responsibility. `GameScreen` maps the serialisable completion type to final UI/persistence without receiving a Phaser object. A copied `CrystalCavernScene` would make shared fixes diverge, while an ECS/manager hierarchy would be excessive for one shared scene and three configuration objects. The scene is still a coordinator and remains the largest module; extracting goal presentation could be reconsidered only if goal types multiply.

**Phase 6 evidence:** `HowToPlay` owns one factual controls/mechanics view reused by the World 1 briefing and About; `game-flow.js` owns three pure UI transition decisions; `GameScreen` coordinates overlays/bridge commands/persistence status; `WorldScene` still owns physics and run time; `player-repository.js` alone adds the achievements query. Panels receive stable data props and never query Supabase. A global store or new manager hierarchy was rejected because these states are route-local; the remaining limitation is that `GameScreen` is still the largest React coordinator and should be split only if another gameplay overlay family appears.

**Phase 6 final audit:** `GameScreen` owns countdown state and presentation but exposes only the existing resume/restart commands to Phaser. `getBackdropCoverLayout` owns one pure render calculation; `WorldScene` supplies dimensions; Crystal's level data supplies the exceptional overscan. `LeaderboardPanel` renders DTOs only, `player-repository.js` owns projection queries, Route Handlers own identity/orchestration and SQL owns atomic run acceptance. `WorldsPage` settles profile, progress, leaderboard and achievement reads independently, so one optional panel failure no longer erases another panel's valid data. This avoids coupling React to cameras, Supabase to Phaser or art exceptions to collision code. An all-purpose UI/game manager or per-world scene was rejected as harder to explain and test; `GameScreen` remains moderately large but its coordination role is coherent for the current overlay set.

**Shrine/balance evidence:** `emerald-jungle.js`, `sunset-ruins.js` and `crystal-cavern.js` own only data differences: world length, collision rectangles, collectibles, risk-route labels, patrols and hazards. `WorldScene` consumes that contract once; `RunState` owns score/duplicate sets; `CombatState` owns power refresh; React owns labels/forms/navigation. The limitation is hand-authored balancing: representative human completion times still require owner playtesting.

## 2. Event-driven programming and handlers

**Implemented files:** `game/core/events.js`, `game/core/game-bridge.js`, `game/core/input-state.js`, `game/core/combat-state.js`, `components/game/game-screen.js`, `components/game/mobile-controls.js`, `game/scenes/world-scene.js`, `game/systems/player-controller.js`, `game/systems/projectile-system.js`, and tests.

**Evidence and justification:** submit/click/change handlers perform one UI responsibility and call narrow helpers. Timers, Escape listeners, animation frames, and guest progress listeners are removed during cleanup. The guest subscription exposes completed IDs rather than internal mutable state. `game/core/events.js` defines serialisable React/Phaser event names so neither side needs the other's internal objects.

**Alternative:** a global event bus for every UI action would reduce prop callbacks but obscure control flow and listener ownership. Directly passing Phaser scenes into React would be convenient but couple two lifecycles and make teardown/testing fragile.

Phase 3A now implements the bridge. React publishes small command payloads; Phaser collision, overlap, timer, and lifecycle handlers publish serialisable state or terminal events. Every `on` call returns an unsubscribe function; `GameScreen`, `PlayerController`, `WorldScene`, and the Phaser game all release listeners/resources during cleanup. `RunState` ignores mutations outside the running state, preventing duplicate completion or Game Over transitions.

**Phase 3B critical discussion:** actual event sources are keyboard/touch input, Arcade collider/overlap callbacks, scene update/timer transitions, Escape, scale resize and scene shutdown. Commands are `input:changed`, `input:release-all`, `game:pause`, `game:resume` and `game:restart`. Domain events include `coin:collected`, `fish:collected`, `power:started`, `power:expired`, `projectile:fired`, `enemy:stomped`, `enemy:defeated`, `player:damaged`, `state:changed`, `world:completed` and `run:ended`. Fish ordering is overlap -> activate rule state -> domain events -> snapshot; completion transitions state before emitting persistence work. Disabled bodies plus `RunState` sets prevent duplicate coin/enemy/completion effects. Bridge subscribers return ownership-specific unsubscribe functions. Scene cleanup removes bridge, keyboard, resize and collider listeners; Phaser disposes groups. A single global bus for React, Phaser and services was rejected because it would hide ownership and allow backend concerns into moment-to-moment gameplay. Direct React callbacks were rejected because they would expose scene objects and couple lifecycles.

**Current correction:** guest progression is not persistent. Welcome emits a reset before client navigation; World Map subscribes to module-memory changes; completion publishes once; unsubscribe removes ownership when the map unmounts. An attempt query value makes repeated game entries distinct and reconstructs `GameScreen`, Phaser and `RunState` without a run manager. Phaser platform collision remains scene-owned, while the pure `canLandOnPlatform` predicate contains only the reusable descending-from-above rule. Session storage was rejected because refresh must reset; React context/global state libraries were rejected as unnecessary.

**Phase 7 evidence:** zero lives freezes Arcade Physics before `run:ended`; React renders the final snapshot and may request a Fish challenge without receiving a scene reference. A correct server response emits `game:revive`; `RunState.revive` rejects timer endings, non-terminal runs and a second revive, then `WorldScene` restores verified safe ground, resumes the same physics scene, publishes state and emits `run:revived`. The mounted `GameScreen` owns and removes both terminal/revival subscriptions. Checkpoint challenges and achievements remain planned.

**Phase 4 evidence:** the World 2 checkpoint is another Arcade overlap source and follows the existing order: guarded `RunState.complete` -> physics pause and final snapshot -> `world:completed` -> React guest or authenticated progression handler. The handler uses `world.number`, so it unlocks World 3 without a World-2-specific callback. Restart emits `game:restart` and recreates the selected level; cleanup ownership is unchanged. Polling the scene from React was rejected because it would duplicate state and miss exact transition edges; direct persistence inside the collision callback was rejected because network lifecycle does not belong to Phaser.

**Phase 4 physics correction:** Arcade produces collision/contact state; the one-way process callback accepts only descending contact from above; losing `blocked.down` immediately returns control to gravity. Crossing the fall boundary invokes `damagePlayer` once per fall, `RunState.damage` guards life/terminal transitions, and `body.reset` synchronises current/previous body state before the next frame. Completion and Game Over remain mutually guarded terminal events. Scene shutdown still removes command, keyboard and collider ownership. Polling positions from React or directly calling persistence from a fall/collision callback would couple lifecycles and add ordering races.

**Navigation optimisation:** selection changes trigger two independent speculative events: `router.prefetch` warms the dynamic route and `preloadWorld` warms only its runtime/textures. Neither declares success. On mount, `GameScreen` subscribes before boot; Phaser loader failure emits `game:load-failed`, while successful scene creation emits `game:ready` and the first `state:changed`. Cleanup marks the async boot inactive, removes window and bridge subscriptions, destroys the single game and prevents late promise resolution from creating another instance. Polling canvas children or using a fixed delay would be simpler but cannot establish real readiness and can produce blank/stale screens.

**Verified runtime evidence:** the production build launched warmed World 1 and World 2 in about 0.77–0.81 seconds with `status=loading` briefly observable, one canvas, and no visible loading overlay; readiness then changed to `playing`. Map return removed all canvases and replay reset score/coins/lives/timer. Desktop 1440×900 and mobile 320×568 had no document scrolling or console errors. Real World 1 completion unlocked World 2; walking unsupported gaps in both worlds removed one life and respawned the player. These checks do not substitute for configured Supabase/OAuth/RLS verification.

**Phase 5 evidence:** keyboard/mobile commands still enter `PlayerController`; Arcade collision/overlap callbacks still own platform, hazard, enemy, fish, projectile and goal contacts. The final sequence is treasure overlap -> guarded run completion -> physics pause -> final snapshot -> `world:completed` -> guest memory or authenticated Route Handler. `RunState.complete` returns false after the first transition, so repeated overlap cannot duplicate victory. Restart reconstructs the same configured scene; shutdown owns bridge/keyboard/collider/system cleanup. Polling player x or declaring victory from React routing was rejected because neither proves collection and both split terminal-state ownership.

**Phase 6 evidence:** Start Adventure is a click event that permits the first Phaser construction; no scene means no pre-start physics/timer. Pause remains a scene command and snapshot. Resume clicks enter one guarded React countdown; effect cleanup cancels obsolete timeouts and only the final edge emits `game:resume`. Escape pauses but cannot resume around the countdown. Checkpoint overlap emits once, then the React handler performs guest or authenticated persistence and enables Next World only on saved state. Restart and route unmount cancel countdown UI and existing scene cleanup removes bridge, keyboard and physics ownership. Polling scene state or direct navigation inside an overlap callback were rejected because they hide ordering and couple Phaser to Next/Supabase.

**Phase 6 final audit:** the concrete ordering is Resume click → `resumeStep=3` → cleanup-owned React timeouts advance 2, 1 and GO → one `game:resume` emission → `WorldScene.setPaused(false)` resumes physics and shifts the paused combat window once. The transparent layer intercepts mobile input during those states; restart sets the step to null before emitting restart, and unmount clears the pending timeout and bridge subscriptions. `RunState` and `CombatState` therefore never advance during the visual countdown. A polling loop or independent Phaser countdown would add another clock and make duplicate prevention/accessible announcements less explicit.

**Shrine/balance evidence:** keyboard/touch events still enter `PlayerController`; Arcade overlaps invoke `collectCoin`, `collectFish`, enemy/hazard handlers and `completeWorld`. Coin ordering is guarded state mutation → body disable → `coin:collected` → snapshot. Fish ordering is active-body check → disable → `CombatState.activate` → `fish:collected`/`power:started` → snapshot; a later fish refreshes to eight seconds rather than stacking. Shrine/treasure ordering is guarded completion → physics pause → bounded celebration → snapshot → `world:completed` → persistence UI. `RunState` sets and terminal status prevent duplicate score/completion. Scene shutdown removes bridge/keyboard/collider owners and kills tracked effect tweens. Polling positions from React or persisting in overlap callbacks remains rejected because it creates race-prone lifecycle coupling.

## 4. Virtual identity, cookies, and authorization

**Implemented files:** `proxy.js`, `lib/supabase/proxy.js`, `lib/auth/session.js`, `lib/auth/redirects.js`, `app/api/auth/*`, `app/auth/callback/route.js`, `app/auth/confirm/route.js`, `components/profile/profile-panel.js`, `.env.example`, and `supabase/migrations/202611050001_phase_2b_auth_and_progress.sql`.

**Evidence and justification:** `@supabase/ssr` refreshes cookie sessions at the Next.js proxy boundary; protected routes call `getClaims()` and use the verified `sub`, never a submitted user ID. OAuth uses PKCE code exchange, email confirmation exchanges a short-lived token hash with `verifyOtp`, and both use allow-listed local return paths. Public and secret keys have separate factories. RLS limits private selects/updates to `auth.uid()`, while direct progression/run writes are revoked. The RLS-bypassing service role has explicit operation-level grants only for current server work and no unused achievement/sequence access. Trusted mutations are atomic functions reached only after server identity and input checks; leaderboard insertion additionally requires an owned, single-use run, World 3 declaration, and persistent completion of all three worlds. Sign Out remains inside the authenticated profile panel. Guests use separate temporary memory and cannot submit leaderboard runs.

**Alternative:** custom password hashes/session tables provide control but add credential, recovery, OAuth, rotation, and cookie-security responsibilities. Client-only local-storage tokens are simpler but script-readable and unsuitable as a server authorization source. Supabase SSR plus RLS was selected for managed identity and layered authorization.

**Phase 7 Fish identity:** authenticated challenge ownership is `auth:<verified sub>` and never accepts a submitted user ID. Guest ownership is `guest:<random uuid>` from a signed HttpOnly, SameSite=Strict, Fish-route-scoped cookie; tampering invalidates the signature and creates a separate identity. Both are further bound to a run-attempt UUID in the server record. The Fish table has RLS enabled, grants no browser role, and is deliberately separate from profiles, progression, ranked runs and achievements.

**Remaining and limitations:** email delivery, Google consent, live cookie refresh, and RLS cross-user denial require a configured Supabase project. The in-memory request guard is a best-effort application layer; distributed production limits must use Supabase/platform controls. Score values still originate in client-side Phaser and therefore cannot be fully cheat-proof. A future trusted gameplay-evidence or server-recomputable score design is required; current checks validate identity, ownership, bounds, progression, World 3 completion, and one-time submission without claiming authoritative scoring.

Authenticated World 1 completion calls `/api/progress` without submitting a leaderboard score; the Route Handler still derives identity from verified claims. Guest completion uses only the in-memory adventure service. This preserves the identity boundary while the later authoritative score design remains explicitly unfinished.

**Phase 3B critical discussion:** gameplay receives only a mode flag and stable progress result. The Route Handler verifies SSR cookie claims and the database function/RLS enforce sequential ownership. Phaser never imports Supabase, cookies or profile data. Keeping guests as anonymous Supabase users was rejected because it would mix guest and account identities and expand RLS/session complexity. Custom session cookies were rejected in favour of Supabase PKCE/SSR refresh because custom credential storage, rotation and OAuth linking add security risk. Configured email/OAuth and deployed RLS remain owner-environment checks, not falsely claimed here.

**Current identity boundary:** guest reset cannot delete or overwrite registered data because it removes only `treasurehunt.guest-progress.v1` and mutates one browser-memory array. Authenticated World Map state still comes from `getPlayerProgress` using the verified cookie identity, and completion still reaches the service-role function only after Route Handler verification. Unit tests prove guest transitions do not mutate supplied authenticated progress. Live persistence across logout/login still requires the configured Supabase project and is not claimed as locally exercised.

## 5. Phase 8 implementation evidence

**High cohesion and low coupling.** Gem/fish/coin/enemy/objective placements remain configuration; `WorldScene` owns Arcade overlaps and emits serialisable events; `RunState` owns duplicate collection and scoring; `GameScreen` owns the bridge-to-HTTP queue and accessible toast; Route Handlers own identity/input validation; SQL owns atomic evidence, aggregate statistics, achievements, progression, and ranking. `lib/game/gameplay-evidence.js` is the small whitelist contract, while `lib/game/achievements.js` contains only badge metadata and guest threshold derivation. A new framework, global store, copied scene, or generic achievement service would add dependency edges without a second implementation.

**Event-driven programming.** A gem body overlap calls `collectGem`, disables that body once, emits `gem:collected`, publishes state, and asynchronously records evidence. Fish and enemy events follow the existing bridge. Compass/treasure ordering is guarded completion → objective event → queued event flush → transactional completion. Newly inserted achievement keys return through the same event request and drive one timed notification; React does not poll Phaser or Supabase. Duplicate collision callbacks are rejected by the run sets and database unique key.

**Interoperability.** React calls stable JSON Route Handlers, not PostgREST tables. Server validation maps event DTOs to existing world configuration; Supabase functions accept verified UUID/world/event primitives and return stable JSON/ranking projections. The Fish HTTP adapter and revival tables are unchanged and absent from this dependency path. Direct Phaser-to-Supabase calls were rejected because they would mix physics lifecycle, provider formats, cookies, and persistence failures.

**Virtual identity and security.** Every authenticated route derives `sub` from verified Supabase claims. Run start checks server progression; event recording and completion lock an owned, active, unsubmitted run; direct browser grants to runs/events/achievements/leaderboard writes remain revoked. Before the completion RPC, the server reloads the owned run and ID-ordered evidence, revalidates every entity against immutable world configuration, rejects duplicates/non-final objectives, requires a conservative traversal minimum, enforces the world timer, and rejects stale/future runs. The completion request contains only duration—score, coins, world, completion state, and user ID are server-derived. Ranked rows are created only for World 3, and the ranking RPC returns no user IDs. Guests never obtain a run or write achievement/profile data. A malicious modified browser can still construct a plausible valid event sequence; eliminating that residual client-evidence risk would require authoritative server simulation or signed deterministic replay. The implementation therefore does not claim cheat-proof rankings.

**Verification evidence and limits.** The Phase 8 migration was dry-run as the only pending migration, deployed to the linked production project, and read-only checks confirmed the new progress columns/ranking RPC plus anonymous denial for the event table and run-start RPC. Vitest covers collectible duplicate guards, temporary guest thresholds, configuration whitelisting, strict duration parsing, server-derived route contracts, and ranking projection. Browser automation reached the local login redirect but had no authenticated session; the Windows controller then stopped on URL-safety confidence. Therefore responsive visual play, registered logout/login persistence, and a genuine completed World 3 leaderboard insertion were not claimed as performed in this handoff.
